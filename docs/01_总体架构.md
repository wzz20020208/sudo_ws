# 总体架构

## 定位

本项目的最终目标：通过 CAN 协议控制**脉塔（MYACTUATOR）RH 系列谐波关节模组**。
电机协议要点（摘自 `docs_cn/电机说明/temp20251201电机使用说明.md`）：

- CAN 1Mbps，标准帧，DLC=8
- 指令 ID `0x140 + ID(1~32)`，应答 ID `0x240 + ID`
- 常用指令：读状态/错误 `0x9A`、速度闭环 `0xA2`、绝对位置闭环 `0xA4`、
  读多圈位置 `0x60`、设零点 `0x64`、读写 PID `0x30/0x32`、系统复位 `0x76`

## 分层架构

```
┌─────────────────────────────────────────────┐
│  App 层（demo / 控制逻辑）      [里程碑 3+]  │
├─────────────────────────────────────────────┤
│  Device 层（电机控制器：单机三环 + 多机）      │  ✅ 里程碑 3
├─────────────────────────────────────────────┤
│  Protocol 层（RH 协议：指令编解码）           │  ✅ 核心命令
├─────────────────────────────────────────────┤
│  Transport 层（CanDriver 抽象）              │  ★ 里程碑 1
│    ├─ SocketCanDriver                        │  ✅ 已实现
│    └─ UsbCanDriver（预留）                   │  ⏳ 后续
└─────────────────────────────────────────────┘
```

设计规则：**上层只依赖相邻下层**，依赖走抽象接口而非具体实现。

- Transport 层只回答「怎么把一帧发出去/收回来」，不关心帧的协议含义。
- Protocol 层只回答「某个指令对应的帧长什么样」，不关心走哪块网卡。
- Device 层组合 Protocol + Transport，暴露给 App 的是一台电机的高级操作
  （设置目标速度/位置、读取状态等）。

## 目录结构

```
include/motor_can/            # 公共头文件（对外 API）
├── common/log.hpp            # 日志宏
└── can/                      # CAN 传输层
src/                          # 实现
├── can/
└── main.cpp                  # App 层 demo
tools/                        # 运维/测试脚本
src/tests/                    # 单元测试
docs/                         # 设计文档
```

## 命名约定

- 命名空间：`motor_can`
- 类：`PascalCase`（如 `SocketCanDriver`）
- 函数/变量：`snake_case`
- 文件：`snake_case`
- 宏（对外日志）：`MC_LOG_*`

## 里程碑规划

| 里程碑 | 内容 | 状态 |
| :-- | :-- | :-- |
| 1 | 骨架 + CAN 传输层（SocketCAN） | ✅ 本次 |
| 2 | 协议层：RH 指令编解码 + 单位换算 | ✅ 核心命令 + 第二批（PID/加速度/编码器/增量·力控位置/单圈角度/模式） |
| 3 | Device 层：单机三环控制 + 多机线程池发布 + 请求/回复过滤 | ✅ 实机通过 |
| 4 | App 层：控制逻辑整合 + GUI 改用 Device 层 + 整机联调 | ⏳ |

> 遵守「不要一步到位」：每个里程碑实现前与用户确认方案，实现后确认结果，
> 再进入下一个里程碑。
