# 跟随 demo 流量估算与丢帧分析

> 场景：`motor_full_control`（GUI）驱动电机1、`example_follow_demo` 读电机1 并驱动电机2，
> 两程序同时运行在共享 can0 上。本文记录流量估算、实测现象与疑似根因（待实测确认）。

## 一、实测现象

| 控制频率 | 现象 | 说明 |
| :-- | :-- | :-- |
| 100Hz（10ms 周期，10ms 回复超时） | **电机2 完全不动** | 只有电机1 能运动（GUI 在驱动它） |
| 10Hz（100ms 周期，100ms 回复超时） | 电机2 动但误差很大 | 100ms 才更新一次，追不上运动中的电机1 |

早期曾把「100Hz 能同步」误记为实测结果，后纠正：100Hz 下电机2 实际不动。

## 二、GUI 消息流（motor_full_control）

- **后台轮询**：QTimer 300ms 一次，每次 0x9A（read_status）+ 0x9C（read_run_status），
  各一请求一回复 → 4 帧/300ms ≈ **13 帧/s**。
- **控制指令**（0xA1/0xA2/0xA4）：点按钮一次性发送，每次 1 命令 + 1 回复，按点击频率计。
- **单电机实例**：ID 可改（默认电机1），不主动发 0x280 广播。

结论：GUI 平时**不是高流量**，不会把总线灌满。

## 三、demo 消息流（100Hz）

每周期 10ms 固定 6 帧：

| 方向 | 帧 | 去向 |
| :-- | :-- | :-- |
| 读角度 | 0x92 → 电机1 | 0x141 |
| 回复 | ← 0x241 | 数据首字节 0x92 |
| 读角度 | 0x92 → 电机2 | 0x142 |
| 回复 | ← 0x242 | 数据首字节 0x92 |
| 位置指令 | 0xA4 → 电机2 | 0x142 |
| 回复 | ← 0x242 | 数据首字节 0xA4 |

= 6 × 100 = **600 帧/s**（另有电机1 侧 GUI 轮询 ~13 帧/s）。

## 四、总线与队列估算

- 总线合计 ≈ **613 帧/s**。标准帧 DLC=8 @1Mbps ≈ 111μs/帧 → 负载 **≈ 6.8%**，远未饱和，
  单帧延迟亚毫秒级。
- **队列动态**：demo 的 0x241 队列净增 ~7 帧/s（GUI 轮询贡献），0x242 进出平衡，深度始终
  <10。`kMaxQueueDepth=256` 上限永不触发。

**结论：按此估算，100Hz 下电机2 应该能动，10ms 回复超时几乎不会被碰到。**
总线拥堵不是「电机2 不动」的原因。

## 五、疑似根因：同一电机 ID 上双线程竞争同一回复队列（待实测确认）

demo 主循环与线程池工作线程**同时**对电机2 做带过滤的请求/回复，抢同一个 0x242 队列：

```
主循环   read_angle(2)     → 发 0x92，等 0x242 中 data[0]==0x92 的回复
工作线程 set_position(2)   → 发 0xA4，等 0x242 中 data[0]==0xA4 的回复
                              ↑ 两个线程从同一个 0x242 队列取帧
```

若工作线程先弹出主循环等的 0x92 回复，`data[0]` 不匹配就当杂帧**丢弃**，主循环
只能等满 10ms 超时。100Hz 下这种竞争概率是 10Hz 的 10 倍，`read_angle(2)` 频繁失败，
触发 demo 循环 `if (read_angle(1) && read_angle(2))` 的短路 → 电机2 收不到位置指令 → 不动。

> ⚠️ 该机制为**推断**，与实测现象（100Hz 不动 / 10Hz 能动但误差大）一致，但尚未用
> 成功率数据证实。需先测量 read(1)/read(2) 各自成功率再定性。

## 六、验证与修复方向

1. **验证**：demo 中打印 read(1)/read(2) 成功率，实测确认是否为 read(2) 挂掉。
2. **修复方向（确认后实施）**：
   - 电机2 的位置写改为**发后不等待回复**（fire-and-forget），工作线程不再占用 0x242 队列；
   - 电机2 角度仅在显示刷新时读（每 100ms 一次），主循环每个控制周期只读电机1、
     每周期必发位置指令，角度用最近一次成功的电机1 角度；
   - 消除同 ID 双线程竞争后，100Hz 指令密度得以保持。

## 七、相关机制小结

- **CAN 总线仲裁**：硬件内建、常开不可关。两帧同时上线时逐位仲裁、低 ID 优先、输家重发，
  与丢帧无关（丢帧来自超时，不是碰撞）。
- **软件过滤**：`Motor::request()`（src/motor/motor.cpp）只收 `0x240+id` 队列中命令字节
  匹配的回复，杂帧丢弃。单进程内有效；**多进程间无仲裁**，GUI 与 demo 能共存全靠
  硬件仲裁 + 各自过滤 + 低流量。
- **同 ID 并发陷阱**：带过滤的请求/回复在同一电机 ID 上并发时，线程间可能互相
  丢弃对方等待的回复（第五节）。这是软件层需要规避的点。
